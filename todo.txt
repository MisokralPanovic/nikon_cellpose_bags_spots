- catch+skip (operational) vs fail-fast (programmer/invariant) exception taxonomy - RESOLVED. New module
  src/spot_detector/exceptions.py, single-root hierarchy (standard Python ecosystem convention, cf.
  requests.exceptions/django.core.exceptions):
    SpotDetectorError(Exception)               - root for all exceptions this package defines intentionally
      FatalPipelineError(SpotDetectorError)     - "this will recur identically on every item, never
                                                   catch-and-continue, let it abort the run"
        DimensionMismatchError(FatalPipelineError, ValueError)  - the one concrete case today: do_3d
                                                   disagrees with actual data, raised by assign_spots_to_mask
                                                   instead of a bare ValueError. Multiple-inherits ValueError

                                                   assigment.py's test_dimension_mismatch_raises) keep working
                                                   unchanged.
  Deliberately a small hierarchy, not just one narrow exception class for the single known case - chosen to
  leave room for future fatal-error cases without redesigning the taxonomy again (tradeoff: more structure
  than strictly needed for one case today, accepted deliberately, not an oversight).
  Wiring: both catch sites in run_pipeline.py (the scene loop in _process_file, the file loop in
  run_pipeline) get `except FatalPipelineError: raise` added BEFORE their existing `except Exception`, so a
  fatal error is never caught-and-logged-and-continued at either level. Once uncaught, it propagates all the
  way out of run_pipeline() and terminates the process via Python's normal unhandled-exception behavior

  file), since the cause (do_3d, a run-wide config setting) would recur identically on every file/scene
  anyway; no custom process-termination machinery needed, letting it propagate uncaught already does this.

3. cluster / parallelization readiness
- DONE (confirmed still true 2026-07-30): segmentation.use_gpu is read - utils.py's _load_cellpose passes
  gpu=config.segmentation.use_gpu to CellposeModel (fixed 2026-07-27, updated to attribute access by the

- no checkpointing/resume for interrupted runs - DEFERRED to the Snakemake migration (2026-07-27 discussion,
  see LEARNING_NOTES.md), not something to hand-build in run_pipeline.py now. Reasoning:
    - overnight-run crash resilience splits into two failure classes: catchable Python exceptions (CUDA
      OOM, corrupt file, etc. - already handled per-file/per-scene, see item 1) vs. the process getting
      SIGKILLed outright (OS OOM killer, preemption, power loss) - the latter can NEVER be caught or logged
      from inside the process, so the only real defense is making sure completed work is already durable on
      disk before the kill, not smarter exception handling. Per-file CSVs already satisfy this; the
      run-level rollup (_run_objects_{MODE}.csv) currently only gets written once at the very end and could
      instead be reconstructed by globbing tab_dir for already-written per-file CSVs - cheap, still open.
    - "redo with a new model/params" vs. "resume a killed run with the same config" need to be told apart,
      or a naive skip-if-exists resume would silently reuse a DIFFERENT config's stale output and blend two
      runs' results under one filename with no visible error. Planned workflow: symlink raw data + fresh
      output folder per analysis variant (matches the old repo-per-run notes at the top of this file) makes
      "redo" safe by construction (nothing to collide with); "resume in place" would need either a config
      fingerprint check or an explicit refuse-to-overwrite-unless-forced guard - not built.
    - Snakemake's DAG + rule params already solve exactly this (only rebuild targets whose inputs/params
      changed) - building a hand-rolled version now risks a weaker, unsafe duplicate of what the planned
      migration (item 3 of the original pre-audit list, `workflow/`) gives for free. Revisit there instead.
- separately (not deferred): after catching a CUDA OOM, call torch.cuda.empty_cache() before continuing to
  the next scene/file - the caching allocator can leave fragmented/reserved memory behind after an OOM, so
  without this the *next* item can fail too even though it would otherwise fit
- fully sequential file/scene loops, no parallel scheduling hooks for snakemake
- GPU memory measured empirically 2026-07-27 (RTX 4060 laptop, 7.8GB total, real .nd2 scene from
  data/None_0.nd2, both configured checkpoints: cpsam_pseudo3d_4x_20260506 + bag_spot_model).
  Numbers are torch.cuda's *reserved* memory (what the OS sees as unavailable to a second
  process), not *allocated* (live tensors) - reserved is the number that matters for deciding
  how many concurrent worker processes fit on one GPU, since the caching allocator doesn't
  release it until the process exits.
    - both models loaded, idle: ~1.8GB reserved
    - peak during one scene (segment + detect), 3D mode: ~2.7GB reserved
    - peak during one scene, 2D mode: ~3.9GB reserved (but see bug below - this ran the
      wrong spotiflow model)
  -> tentative verdict: process-per-GPU-slice parallelization looks feasible on shared cluster
     GPUs with >=16-24GB (2-4 concurrent workers with headroom); tight on an 8GB card (1 worker
     safely, 2 only with no other tenant and some risk). NOT yet a green light - the test scene
     had only 1 object / 18-49 spots, and Cellpose's flow-field postprocessing memory scales with
     instance count, not just image size, so a busy real FOV (dozens-hundreds of BAGs) needs the
     same measurement before sizing cluster GPU requests. Re-run probe against a representative
     high-density scene before committing to a parallel worker count.
  -> BUG surfaced during this measurement: config.yml has mode.do_3d: false, but the configured
     spotiflow_models_path (bag_spot_model) is a 3D-only model. ModelBundle's documented fallback
     chain (utils.py) catches the mismatch and silently substitutes the generic pretrained
     synth_complex model instead of raising - so a real 2D run today silently skips the user's
     trained spot model. Either do_3d should be true, or spotiflow_models_path needs a 2D-trained
     model - needs a decision, not just a fallback.
  -> concurrency stress test 2026-07-27: ran 2 concurrent 2D-mode workers for real on the 8GB
     card (worst case ~3.9GB/worker individually). Both completed correctly, peak COMBINED memory
     via nvidia-smi (not torch's self-reported stats) = ~6.96GB - but worker 2's log shows a
     transient CUDA OOM warning mid-run (~80MB free at that instant) that the allocator recovered
     from. Conclusion: 8GB is maxed out / not safe for 2 workers in production. On 12GB that
     leaves ~5.3GB headroom over the observed peak, so 2 workers should fit reliably there - but
     re-run this same concurrency test against a dense real scene (many objects/spots, not the
     1-object/49-spot calibration scene used so far) before finalizing worker count for the
     cluster request.

6. segmentation correctness   <- BUG CONFIRMED 2026-07-28, not yet fixed (found while pydantic-validating
   bin_factor, deliberately deferred to stay scoped to the config migration)
- segment_2d/segment_3d (segmentation_detection.py): block_reduce() does NOT require bin_factor to evenly
  divide the image shape - it silently zero-pads up to the next multiple before reducing (verified:
  skimage.measure.block_reduce on a (513,513) image with factor=4 returns (129,129), not an error).
  masks.repeat(factor, ...) then scales back up by exactly `factor`, landing on the PADDED size (516,516),
  not the original (513,513) - masks_cleaned ends up larger than bf_stack whenever image dims aren't evenly
  divisible by bin_factor. No crash anywhere in the chain.
- downstream impact: assign_spots_to_mask (run_pipeline.py) indexes into this oversized `masks` using spot
  coordinates from the full-resolution, UNBINNED spot_stack - indices still land in-bounds (no crash), but
  mask content near the edges is corrupted (zero-padding got averaged into the last real block before
  Cellpose even ran) and everything downstream (edge-mask stripping, spot assignment, QC overlays) works
  off a shifted/wrong-shaped array. Silent, dimension-dependent - only bites on scenes whose shape isn't
  evenly divisible by bin_factor, so easy to miss in testing against one well-behaved image size.
- explicitly NOT something PipelineConfig/SegmentationConfig can validate: divisibility depends on each
  image's shape, which isn't known until BioImage opens the file - one config.yml runs across every
  file/scene in raw_data_dir, and they aren't guaranteed to share dimensions.
- fix belongs in segmentation_detection.py. Two real options discussed 2026-07-28, neither picked yet:
    (a) crop the upscaled mask back to original shape - masks_resized[:orig_shape] on each axis before
        edge-mask removal; simple, keeps output aligned, discards the few padded pixels (never real data)
    (b) fail fast - check image_shape[i] % factor == 0 at the top of segment_2d/segment_3d and raise
        ValueError naming the offending scene, instead of silently producing misaligned output
  leaning (a) since it's a real fix rather than just surfacing the limitation, but not decided.
